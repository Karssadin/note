## 什么是粘包（Packet Sticking）

**粘包**是指发送方连续发送多个数据包，接收方一次 `recv()` 时，**接收到的数据混合了多个完整/不完整的消息**，无法正确区分消息边界的现象。

```
发送方先后发送：[消息A] [消息B]
接收方收到：  [消息A+消息B]  或  [消息A前半][消息A后半+消息B]
```

---

## 产生原因

**1. TCP 是面向字节流的协议**

TCP 只保证数据**有序、完整**到达，不保证以发送时的消息边界到达。发送方的多次 `send()` 可能被合并为一次传输。

**2. Nagle 算法**

为了减少小包数量，Nagle 算法会将小数据缓冲，等到确认（ACK）到达或缓冲区达到 MSS（最大报文段大小）时再发送，导致多个小消息被合并。

**3. 发送缓冲区 / 接收缓冲区**

- 发送端：多次 `send()` 的数据积压在内核缓冲区，一次性发出
- 接收端：接收缓冲区一次读取了多个消息的数据

**4. MTU/MSS 限制**

一个大消息可能被拆成多个 TCP 段传输（分包），接收端需要自行重组。

**UDP 不存在粘包**：UDP 是面向报文的，每个报文保留独立边界，`recvfrom()` 一次只返回一个完整报文。

## 解决方案

### 1. 固定长度消息

每条消息固定为 N 字节，接收方按固定长度读取：

```cpp
char buf[MSG_SIZE];
int total = 0;
while (total < MSG_SIZE) {
    int n = recv(fd, buf + total, MSG_SIZE - total, 0);
    total += n;
}
```

- **优点**：简单
- **缺点**：消息长度不统一时浪费空间

### 2. 分隔符（Delimiter）

在每条消息末尾加特殊分隔符（`\n`、`\r\n`、`\0` 等）：

```
[数据A]\n[数据B]\n
```

接收方按分隔符切割。**HTTP 协议**即使用 `\r\n` 分隔头部字段。

- **缺点**：消息内容中不能包含分隔符，或需转义

### 3. 消息头 + 消息体（TLV/Length-Prefix）

**最常用方案**：在消息前添加固定大小的头部，其中包含消息体长度：

```
[4字节长度字段][消息体数据]
```

```cpp
struct MsgHeader {
    uint32_t length;  // 消息体长度（网络字节序）
};

// 发送
uint32_t len = htonl(body.size());
send(fd, &len, 4, 0);
send(fd, body.data(), body.size(), 0);

// 接收
uint32_t len;
recv(fd, &len, 4, MSG_WAITALL);
len = ntohl(len);
std::string body(len, '\0');
recv(fd, body.data(), len, MSG_WAITALL);
```

- **优点**：灵活，消息长度可变
- **广泛应用**：Redis RESP 协议、Protobuf、RPC 框架

### 4. 关闭 Nagle 算法

对实时性要求高的场景（如游戏），可设置 `TCP_NODELAY`：

```cpp
int flag = 1;
setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
```

- **缺点**：增加小包数量，网络带宽利用率下降

## 常见协议的处理方式

| 协议 | 解决粘包方式 |
|------|-------------|
| HTTP/1.1 | `Content-Length` 头 + `\r\n\r\n` 分隔头/体 |
| HTTP/2 | 帧（Frame）机制，帧头含长度字段 |
| Redis RESP | `*3\r\n$3\r\nSET\r\n...` 行协议 |
| WebSocket | 帧头含 payload length |
| Protobuf | 需应用层自行加长度前缀 |
