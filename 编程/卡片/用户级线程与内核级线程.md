## 对比总览

| 维度 | 用户级线程（ULT） | 内核级线程（KLT） |
|------|-----------------|-----------------|
| 管理方 | 用户空间的线程库 | 操作系统内核 |
| 内核感知 | 内核不知道线程存在 | 内核直接管理 |
| 上下文切换 | 无系统调用，速度快 | 需要陷入内核，较慢 |
| 调度 | 用户库负责 | 内核负责 |
| 阻塞行为 | 一个线程阻塞→整个进程阻塞 | 一个线程阻塞不影响其他线程 |
| 多核并行 | **不支持**（进程只有一个内核调度实体）| **支持**（多线程可分配多核）|
| 创建/切换开销 | 低 | 高 |
| 典型实现 | 早期 POSIX 线程库、Go goroutine（部分） | Linux pthread、Java Thread |

---

## 用户级线程（ULT）

**优点**：
- 切换不需要系统调用，代价极低
- 可以自定义调度策略（如协程）
- 可在不支持线程的 OS 上实现

**缺点**：
- 任何阻塞系统调用（如 `read()`）都会导致整个进程阻塞
- 无法利用多核（内核只看到一个进程）
- 实现复杂（需要包装阻塞系统调用为非阻塞）

---

## 内核级线程（KLT）

**优点**：
- 一个线程阻塞，其他线程可继续运行
- 支持多核并行执行
- 内核可以根据全局状态做最优调度

**缺点**：
- 创建、切换、销毁均需系统调用，开销较大
- 线程数量受内核资源限制

---

## 混合模型（Many-to-Many）

现代 OS 通常采用 **M:N 混合模型**：M 个用户级线程映射到 N 个内核线程（M ≥ N）：
- 兼顾 ULT 的低切换开销和 KLT 的多核能力
- 线程库（如 Solaris LWP、Go 运行时）在用户空间维护调度，内核线程作为"工人"

**Go 运行时** 是典型实现：
- Goroutine（用户级，百万级并发）
- 映射到 `GOMAXPROCS` 个 OS 线程（内核级）
- 调度器（`G-P-M` 模型）在用户空间实现 Work Stealing

## 实际语言对应

| 语言/运行时 | 线程模型 |
|------------|---------|
| C/C++ pthread | 内核级线程（1:1）|
| Java Thread | 内核级线程（1:1）|
| Go goroutine | 混合（M:N）|
| Python threading | 内核级线程，但受 GIL 限制 |
| C++20 coroutine | 用户级（协程，单线程内切换）|
