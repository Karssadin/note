## 三大日志概述

MySQL InnoDB 涉及三种核心日志：

| 日志 | 层级 | 类型 | 作用 | 写入时机 |
|------|------|------|------|---------|
| undo log | InnoDB 引擎层 | 逻辑日志（反操作） | 事务回滚、MVCC 版本链 | 数据修改前 |
| redo log | InnoDB 引擎层 | 物理日志（页修改） | 崩溃恢复（crash-safe） | 事务执行中持续写入 |
| binlog | Server 层 | 逻辑日志（SQL/行变化） | 主从复制、数据恢复 | 事务提交时 |

## undo log（回滚日志）

### 作用

1. **事务回滚**：记录数据修改前的旧值，事务失败时恢复原始数据，保证原子性
2. **MVCC**：通过版本链为并发读提供历史快照，实现读不阻塞写

### 工作方式

不同操作生成不同的 undo log：
- **INSERT**：记录主键 → 回滚时按主键 DELETE
- **DELETE**：记录整行数据 → 回滚时重新 INSERT
- **UPDATE**：记录被修改列的旧值 → 回滚时恢复

### 版本链与 MVCC

每条 undo log 包含 `trx_id`（事务 ID）和 `roll_pointer`（指向上一个版本），多次修改形成版本链。事务读取数据时，沿版本链查找对自己可见的版本（详见 [[事物|事务]] 中的 Read View 机制）。

undo log 本身也写入 [[Buffer Pool]] 的 Undo 页，修改 Undo 页后同样需要记录 redo log 以保证持久化。

## redo log（重做日志）

### 为什么需要 redo log

数据修改先在 [[Buffer Pool]] 内存中完成（标记为脏页），如果此时崩溃，脏页数据丢失。redo log 的作用：
1. **crash-safe**：崩溃重启后，根据 redo log 恢复已提交但未刷盘的数据
2. **性能优化**：将数据页的随机写转换为 redo log 的顺序写（WAL 技术）

### WAL 技术

WAL（Write-Ahead Logging）：先写日志，再写磁盘。

更新数据时：修改 Buffer Pool 内存 → 写 redo log → 返回成功。脏页由后台线程异步刷盘。顺序写 redo log 比随机写数据页快得多。

### redo log 刷盘策略

redo log 先写入 redo log buffer（默认 16MB），再根据策略持久化：

| `innodb_flush_log_at_trx_commit` | 行为 | 安全性 | 性能 |
|----------------------------------|------|--------|------|
| 0 | 事务提交时不刷盘，后台线程每秒刷 | 最低（崩溃丢 1 秒数据） | 最高 |
| **1**（默认） | 每次提交都 fsync 到磁盘 | 最高（不丢数据） | 最低 |
| 2 | 每次提交写到 OS page cache，后台线程每秒 fsync | 中等（OS 崩溃才丢数据） | 中等 |

### 循环写入

redo log 由固定大小的文件组组成（默认 2 个文件，如 ib_logfile0 和 ib_logfile1），以环形方式循环写入：
- `write pos`：当前写入位置
- `checkpoint`：当前可擦除位置（对应的脏页已刷盘）
- write pos 追上 checkpoint 时，redo log 写满，MySQL 阻塞，等待脏页刷盘后 checkpoint 前进

### redo log vs undo log

| 维度 | redo log | undo log |
|------|----------|----------|
| 记录内容 | 事务完成后的数据状态（新值） | 事务开始前的数据状态（旧值） |
| 崩溃处理 | 已提交事务 → 用 redo log 恢复 | 未提交事务 → 用 undo log 回滚 |

## binlog（归档日志）

### 与 redo log 的区别

| 维度 | redo log | binlog |
|------|----------|--------|
| 层级 | InnoDB 引擎层 | Server 层（所有引擎通用） |
| 内容 | 物理日志（某页某偏移的修改） | 逻辑日志（SQL 语句或行变化） |
| 写入方式 | 循环写（固定大小，会覆盖） | 追加写（写满创建新文件，保留全量） |
| 用途 | 崩溃恢复 | 主从复制、数据备份恢复 |

### 三种格式

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| STATEMENT | 原始 SQL 语句 | 日志量小 | 动态函数（now()、uuid()）导致主从不一致 |
| ROW | 行数据最终修改结果 | 精确，无动态函数问题 | 批量操作日志量大 |
| MIXED | 自动选择 STATEMENT 或 ROW | 兼顾两者 | 复杂度高 |

### binlog 刷盘策略

binlog 先写入每个线程的 binlog cache，事务提交时写入 binlog 文件：

| `sync_binlog` | 行为 |
|----------------|------|
| 0（默认） | 每次提交只 write 到 page cache，由 OS 决定何时 fsync |
| **1** | 每次提交都 fsync 到磁盘（最安全） |
| N (N>1) | 累积 N 个事务后 fsync（性能与安全折中，生产常用 100~1000） |

### 仅依赖 binlog 能否实现 crash-safe

不能。binlog 是全量追加日志，不记录数据页状态，无法判断崩溃时哪些数据已落盘。所以 InnoDB 引入 redo log 弥补这一缺陷。

## 执行 UPDATE 的完整流程

以 `UPDATE t_user SET name = 'xiaolin' WHERE id = 1;` 为例：

1. 连接器验证身份 → 解析器词法语法分析 → 优化器选择主键索引 → 执行器调用引擎接口
2. InnoDB 通过主键索引查找数据页，加载到 Buffer Pool（若不在内存中）
3. 记录 **undo log**（旧值），写入 Buffer Pool 的 Undo 页
4. 更新 Buffer Pool 中的数据页（标记为脏页），写 **redo log**（此时 redo log 处于 prepare 状态）
5. 执行器生成 **binlog**，写入 binlog cache
6. **两阶段提交**：
   - prepare 阶段：redo log 持久化到磁盘（状态 = prepare）
   - commit 阶段：binlog 持久化到磁盘 → redo log 状态改为 commit

## 两阶段提交

### 为什么需要

redo log 和 binlog 是两个独立的日志，如果不协调提交顺序，可能出现半成功状态：
- 只写了 redo log、binlog 未写 → 主库有新数据，从库没有 → **主从不一致**
- 只写了 binlog、redo log 未写 → 主库崩溃恢复后没有新数据，从库有 → **主从不一致**

### 提交流程

```
事务提交
  ├── prepare 阶段：写 XID 到 redo log（状态=prepare）→ fsync redo log
  └── commit 阶段：写 XID 到 binlog → fsync binlog → redo log 状态改为 commit
```

### 崩溃恢复

MySQL 重启后扫描 redo log，对处于 prepare 状态的事务：
- binlog 中**有**对应 XID → 提交事务（数据不丢）
- binlog 中**无**对应 XID → 回滚事务

判断标准：**binlog 写成功 = 事务提交成功**。

### 未提交事务的 redo log 会持久化吗

会。后台线程每秒将 redo log buffer 刷盘，不管事务是否提交。但崩溃恢复时，未提交的事务会根据 binlog 缺失被回滚，不影响一致性。

## 组提交

### 两阶段提交的性能问题

"双 1" 配置（`sync_binlog=1` + `innodb_flush_log_at_trx_commit=1`）下，每个事务提交需要 2 次 fsync（redo log + binlog），磁盘 I/O 压力大。

### 组提交机制

将多个事务的刷盘操作合并为一次，commit 阶段拆为三步：

1. **flush 阶段**：多个事务的 redo log 一次 fsync → binlog 写入文件（不刷盘）
2. **sync 阶段**：多个事务的 binlog 合并一次 fsync
3. **commit 阶段**：各事务按顺序做 InnoDB commit

每个阶段有独立队列，第一个进入的事务成为 Leader，负责带领整组完成操作。

### 优化参数

- `binlog_group_commit_sync_delay`：等待 N 微秒再 fsync，聚合更多事务
- `binlog_group_commit_sync_no_delay_count`：队列中事务数达到 N 个立即 fsync

MySQL 5.7 起 redo log 也支持组提交（prepare 阶段推迟到 flush 阶段合并）。

### 磁盘 I/O 高的优化方法

1. 设置组提交参数，延迟 binlog 刷盘时机
2. `sync_binlog` 设为 100~1000，累积 N 个事务后 fsync
3. `innodb_flush_log_at_trx_commit` 设为 2，redo log 写到 OS page cache

风险：主机掉电时可能丢失最近 1 秒或 N 个事务的数据。

## 主从复制

主从复制依赖 binlog，详见 [[主从复制与高可用]]。

基本流程：
1. 主库写 binlog，提交事务
2. 从库 I/O 线程连接主库 log dump 线程，拉取 binlog 写入 relay log
3. 从库 SQL 线程读取 relay log 重放，更新存储引擎数据

复制模式：异步复制（默认，可能丢数据）、半同步复制（等至少一个从库确认）、同步复制（全部确认，性能差）。
