## 主从复制

### 原理

主库写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放 relay log。

```
主库：事务提交 → 写 binlog
         ↓
从库 IO 线程：连接主库 log dump 线程 → 拉取 binlog → 写入 relay log
         ↓
从库 SQL 线程：读取 relay log → 重放 → 更新存储引擎数据
```

### 复制模式

| 模式 | 说明 | 特点 |
|------|------|------|
| 异步复制（默认） | 主库提交后不等待从库确认 | 性能高，但主库宕机可能丢数据 |
| 半同步复制 | 主库等待至少一个从库确认收到 binlog | 兼顾性能和安全 |
| 同步复制 | 主库等待所有从库确认 | 最安全但性能最差，实际几乎不用 |

### 延迟原因

- 网络延迟
- 从库单线程重放（5.7+ 支持基于组提交的并行复制）
- 从库硬件性能不足
- 大事务（一个事务修改大量数据）

## 读写分离

- 写操作走主库，读操作走从库，降低主库压力
- 实现方式：
  - 应用层路由（代码中判断读写分发）
  - 中间件：ProxySQL、MyCat、ShardingSphere
- 主从延迟导致读到旧数据的解决：
  - 关键业务强制走主库读
  - 等待从库追上（判断 `Seconds_Behind_Master`）

## 高可用方案

| 方案 | 说明 |
|------|------|
| MHA | 自动主从切换，监控主库状态，故障时提升从库 |
| MySQL Group Replication | 基于 Paxos 的多主复制，自动成员管理 |
| InnoDB Cluster | Group Replication + MySQL Router + MySQL Shell 的集成方案 |
| Orchestrator | 拓扑可视化 + 自动故障转移 |

从库数量不宜过多（通常 1 主 2~3 从），过多从库会增加主库 log dump 线程的压力和网络带宽消耗。
