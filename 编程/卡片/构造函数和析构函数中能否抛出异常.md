## 构造函数中能否抛出异常

**语法上可以**，但逻辑上需要谨慎。

```cpp
class Foo {
    int* data;
public:
    Foo() {
        data = new int[100];
        if (some_condition)
            throw std::runtime_error("构造失败");  // 语法合法
        // 但 data 的内存泄漏了！
    }
};
```

**风险**：若构造函数中途抛出异常，**析构函数不会被调用**（对象未完全构造），已申请的资源（堆内存、文件描述符等）会泄漏。

**最佳实践**：
1. 使用 **RAII** 管理资源（用智能指针、RAII 包装类），即使构造中途抛出，子对象的析构函数仍会被调用：

```cpp
class Foo {
    std::unique_ptr<int[]> data;
public:
    Foo() : data(std::make_unique<int[]>(100)) {
        if (some_condition)
            throw std::runtime_error("构造失败");
        // data 自动释放，无内存泄漏
    }
};
```

2. 若必须使用裸指针，在抛出前手动释放已申请资源

## 析构函数中能否抛出异常

**强烈不建议**，实际上是一种错误实践。

**原因 1：双重异常导致 `std::terminate`**

当栈展开（stack unwinding）处理某异常时，C++ 会依次调用局部对象的析构函数。若此时析构函数也抛出异常，就会有**两个异常同时存在**，C++ 规范要求调用 `std::terminate()` 直接终止程序：

```cpp
class Foo {
public:
    ~Foo() { throw std::runtime_error("析构中抛异常"); }  // 危险！
};

void bad() {
    Foo f;
    throw std::logic_error("第一个异常");  // 栈展开时调用 f.~Foo()
    // f.~Foo() 又抛异常 → std::terminate() 终止程序
}
```

**原因 2：资源泄漏**

析构函数抛出异常后，异常点之后的代码（如 `delete[]`、`close(fd)` 等）不会执行，导致资源泄漏。

**最佳实践**：
- 析构函数应标记为 `noexcept`（C++11 起析构函数默认即为 `noexcept`）
- 若析构中必须执行可能失败的操作，在内部捕获并处理（或记录日志），不要让异常传播出析构函数：

```cpp
~Foo() noexcept {
    try {
        cleanup();  // 可能抛出
    } catch (...) {
        // 捕获后忽略或记录日志，不重新抛出
    }
}
```

## 异常安全保证（Exception Safety Guarantees）

| 级别 | 描述 | 典型手段 |
|------|------|---------|
| **nothrow**（无异常保证）| 函数保证不抛出异常 | `noexcept`，析构函数应达到此级别 |
| **strong**（强异常保证）| 操作失败则回滚，程序状态不变（commit-or-rollback）| copy-and-swap 惯用法 |
| **basic**（基本异常保证）| 操作失败后资源无泄漏，程序处于有效状态 | RAII |
| **none**（无保证）| 任何事情都可能发生 | 应避免 |
