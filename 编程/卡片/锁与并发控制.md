## 按粒度的锁分类

- 全局锁：作用于整个数据库，主要是为了全库备份或者某些全库操作而设计。
- 表级锁：
    - 表锁：直接对整张表加锁，包括：
        - 共享锁：允许一个表在其上有多个并发读取操作，但不允许任何写入。
        - 排他锁：允许在表上有一个写入操作但不允许其他任何其他操作（读/写）。
    - 元数据锁：确保多个事务可以正确地并发地执行，并确保在一个事务读取或修改数据时，DDL语句不会进行。
    - 意向锁：是InnoDB为了在表上能更高效地支持多个粒度的锁定而使用的一种锁策略。意向锁分为意向共享锁和意向排他锁，是为了在表中同时存在行级锁和表级锁。
    - AUTO-INC锁：专门为InnoDB表的自增长列设计的。
- 行锁：
    - Record Lock：锁定某一行记录。
    - Gap  
        Lock：锁定一个范围，但不包括任何实际的行记录，主要用于防止幻读。  
        
    - Next-key  
        Lock：是Gap锁和Record锁的结合，它锁定一个范围并包括一个具体的行记录。这是InnoDB默认的锁策略，因为它可以同时处理等值查询和范围查询。  
        

### 全局锁

- 定义：MySQL中的全局锁会锁定整个数据库，使其处于只读状态。数据的增删改操作、表结构的更改，都被阻塞
- 使用`FLUSH TABLES WITH READ LOCK`命令来设置全局锁。
- 使用`UNLOCK TABLES`命令来释放全局锁。
- 应用场景：主要用于全库备份。但这种方法的缺点是，当数据库内容很大时，锁定的时间可能会很长，这可能会导致长时间的业务中断。
- 备份策略：数据库的引擎支持的事务支持可重复读的隔离级别，那么在备份数据库之前先开启事务，会先创建  
    Read View，然后整个事务执行期间都在用这个 Read View，而且由于 MVCC  
    的支持，备份期间业务依然可以对数据进行更新操作。因为在可重复读的隔离级别下，即使其他事务更新了表的数据，也不会影响备份数据库时的  
    Read  
    View，这就是事务四大特性中的隔离性，这样备份期间备份的数据一直是在开启事务时的数据。  
    

### 表锁：共享锁、排他锁(独占锁)

- **表锁**是数据库中的一种锁定机制，按其字面意义，它**会锁住整张数据表**。MySQL支持两种表锁：共享锁（读锁）和排他锁（写锁）。
    - **共享锁**：当一个线程获得一张表的共享锁时，该线程可以读取表，但不能进行修改。其他线程只能获得该表的共享锁，但不能获得排他锁。
    - **排他锁**：当一个线程获得一张表的排他锁时，该线程可以读取和修改表。在此期间，其他线程不能获得该表的任何锁定，这意味着其他线程既不能读也不能写。

```SQL
//表级别的共享锁，也就是读锁；
lock tables t_student read;
//表级别的独占锁，也就是写锁；
lock tables t_stuent write;
//释放锁
UNLOCK TABLES;
```

- 表锁会限制表的并发操作。例如，当一张表被共享锁锁定时，任何其他的写请求都会被阻塞；同样，当一张表被排他锁锁定时，任何其他的读写请求都会被阻塞。
- lock tables  
    语法除了会限制别的线程的读写外，也限定了本线程接下来的操作对象。  
    
- InnoDB存储引擎优先使用行锁，但在某些情况，如没有适当索引的查询或某些全表操作，它仍会使用表锁。表锁是MyISAM的默认锁定策略。在执行全库备份或对整张表进行操作时，经常使用表锁。

### 表锁：元数据锁

- **元数据锁（MDL）**是MySQL引入的一个特定的锁策略，不需要显示使用，在访问一个表的时候会自动加上
- 当执行基于某表的CRUD操作时，MySQL会自动为这张表添加一个**MDL读锁**。允许多个会话并发读取表，但不允许其他会话进行结构更改。意味着，在MDL读锁存在的情况下，其他会话仍然可以查询表，但不能执行如ALTERTABLE这样的DDL操作。
- 当尝试修改表的结构，例如通过ALTERTABLE命令，MySQL会为该表添加一个**MDL写锁**。在其存在时，不允许其他会话读取或修改表。
- 主要目的是确保在对表进行CRUD操作时，表的结构保持不变。例如，一个会话正在查询一个表，而另一个会话希望修改该表的结构。如果没有MDL锁，查询操作可能会返回意外的结果或出现错误。**事务结束之后才释放锁**
    - 如果有一个事务对表添加了MDL读锁，并长时间未提交，那么任何尝试更改表结构的操作都会被阻塞，直到原始事务完成。
    - **写锁优先于读锁**：当有MDL写锁等待时，后续的读锁请求也会被阻塞，这可能导致大量的查询操作被阻塞。
    - 在进行表结构变更之前，建议先检查是否有长时间运行的事务持有表的MDL读锁。这可以通过SHOW  
        PROCESSLIST命令来实现。如果有长时间运行的事务，考虑结束它们，然后再进行表结构变更。  
        

### 表锁：意向锁

- 意向锁是为了优化表锁和行锁之间的冲突检查。
- **意向共享锁**：当事务想要对一个记录加共享锁时，会首先对整张表加意向共享锁。
- **意向独占锁**：当事务想要对一个记录加独占锁时，会首先对整张表加意向独占锁。

- 用于自增字段的值分配。

### 行级锁：插入意向锁

- 插入意向锁是特殊类型的间隙锁，用于插入操作。当一个事务尝试在已有间隙锁的区间内插入记录时，会产生插入意向锁并进入等待状态，直至间隙锁释放。这种锁机制有助于维持数据的一致性和防止幻读。

## 死锁

- 死锁是由于两个事务各自持有对方需要的锁（间隙锁），同时又尝试获取对方持有的锁（插入意向锁），导致彼此相互等待对方释放锁，从而无法继续执行。在数据库操作中，特别是在涉及到多个事务并发执行更新和插入操作时，应该特别留意死锁的可能性，并采取相应的策略来预防或解决死锁问题。

### 预防死锁

- **设计时间：** 在设计阶段，考虑数据库结构和应用程序逻辑，以减少死锁的可能性。例如，使用适当的索引和合理的表设计可以减少查询的复杂性和执行时间，从而减少死锁的风险。
- **避免不必要的事务：** 简化事务逻辑，避免在事务中执行复杂的查询或长时间的操作。
- **按固定顺序访问资源：** 如果多个事务都按照相同的顺序访问资源（如表或行），则可以减少死锁的可能性。
- **避免大事务：** 尽量将大事务拆分为多个小事务，这样可以减少锁定资源的时间，降低死锁发生的概率。
- **使用锁的最小集：** 只锁定需要的数据，不要过度锁定。

### 避免死锁的策略

- 设置事务等待锁的超时时间（通过`**innodb_lock_wait_timeout**`）。
- 开启主动死锁检测（通过`**innodb_deadlock_detect**`）。

### 死锁及其解决方法

  

- **设置锁等待超时：** 通过设置`**innodb_lock_wait_timeout**`参数，可以定义一个事务在等待锁定资源时的最长时间。超时后，事务会被回滚，从而解除死锁。
- **死锁检测：** 启用`**innodb_deadlock_detect**`，当检测到死锁时，InnoDB会自动选择并回滚造成死锁的事务之一，以解除死锁。
- **监控和日志：** 定期监控数据库的性能和死锁日志，可以帮助及时发现和解决死锁问题。
- **重试机制：** 在应用程序中实现重试逻辑，当事务由于死锁被回滚时，可以自动重试。
- **优化查询：** 分析和优化导致死锁的查询，可能需要重新设计查询或更改数据库结构。

---

  

- **互斥条件**：资源不能在同一时刻由多个事务共享。
- **持有并等待**：一个事务持有了某些资源的锁，并等待其他资源上的锁。
- **非抢占条件**：资源不能被强行从占有它的事务那里抢夺过来，只有该事务释放后其他事务才能获取。
- **环路等待**：存在一组事务，其中每个事务都在等待一个由该组其他事务持有的资源。
- 死锁检测与死锁解除：数据库系统提供死锁检测工具，当检测到死锁时，选择一个或多个事务进行回滚以解除死锁。这种方法可能会浪费更多的资源，因为事务可能在执行很长时间后才被回滚。
- 设置锁超时：设置一个锁的超时时间。如果事务在指定的时间内不能获得锁，它会自动回滚。
- 死锁预防：破坏死锁的四个必要条件之一。

  

## 行级锁加锁方式

### 什么SQL语句会加锁

1. **锁定读语句**：使用`**SELECT ... FOR UPDATE**`和`**SELECT ... LOCK IN SHARE MODE**`来显式地对读取的记录加上独占锁（X锁）或共享锁（S锁）。这两个语句必须在事务中使用，锁会在事务提交时释放。
2. **更新和删除操作**：`**UPDATE**`和`**DELETE**`语句默认加独占锁（X锁）。
    
    ```SQL
    sqlCopy code
    UPDATE table SET column = value WHERE id = 1; -- 对id为1的记录加X锁
    DELETE FROM table WHERE id = 1; -- 对id为1的记录加X锁
    
    ```
    
    共享锁和独占锁的特性是：
    
    - 共享锁（S锁）允许读取但不允许写入。
    - 独占锁（X锁）既不允许其他事务读取也不允许写入。

### 行级锁种类

- 行级锁的种类根据隔离级别有所不同。在读已提交（Read Committed）隔离级别下，行级锁主要是记录锁。而在可重复读（Repeatable Read）隔离级别下，行级锁包括记录锁、间隙锁以及Next-Key Lock。

1. **记录锁（Record Lock）**：锁定单条记录。
2. **间隙锁（Gap Lock）**：锁定一个范围，但不包含记录本身，用于防止幻读。
3. **Next-Key Lock**：记录锁和间隙锁的结合，锁定一个范围及其中的记录。

### 行级锁的具体场景

- **唯一索引等值查询**：当查询记录存在时，会在该记录上加上记录锁。如果查询记录不存在，则加上间隙锁。
- **唯一索引范围查询**：对于`**<**`, `**<=**`, `**>**`, `**>=**`的查询，MySQL会在扫描到的每个索引记录上加上Next-Key Lock。在某些情况下，锁可能会退化为记录锁或间隙锁。
- **非唯一索引等值查询**：同时会对二级索引和主键索引加锁。如果查询记录存在，则对二级索引加Next-Key Lock，并在满足条件的主键索引上加记录锁。如果查询记录不存在，则在二级索引上加间隙锁，不对主键索引加锁。
- **非唯一索引范围查询**：对二级索引记录加Next-Key Lock，不会有退化为记录锁或间隙锁的情况。
- **没有加索引的查询**：如果查询语句不使用索引，或者查询不走索引，会导致全表扫描。这种情况下，MySQL会在每条记录上加Next-Key Lock，相当于锁定整张表。

## update没加锁会锁全表？

### 为什么

- **InnoDB的行级锁**：InnoDB默认使用行级锁，但它实际上锁的是索引项而非单纯的行。如果一条`**UPDATE**`语句未使用索引，则InnoDB无法定位到特定的索引项，因此可能会对整个表进行扫描并加锁。
- **Next-Key Locks**：InnoDB利用next-key锁（记录锁和间隙锁的组合）来防止幻读。这种锁不仅锁定具体的记录，还锁定记录之间的间隙。
- **全表扫描**：如果`**UPDATE**`语句的`**WHERE**`子句没有使用到索引，InnoDB可能进行全表扫描。在扫描过程中，会对扫描到的每一条记录加上next-key锁，最终可能导致整张表被锁定。

### 如何避免

- **使用索引**：确保`**UPDATE**`语句的`**WHERE**`子句使用有效的索引。如果存在适当的索引，InnoDB只会锁定索引覆盖的记录，而不是全表。
- **优化器选择**：有时即使`**WHERE**`子句包含索引列，优化器也可能选择全表扫描，特别是在估计使用索引的成本较高时。在这种情况下，可以使用`**FORCE INDEX**`来指定一个索引，强制优化器使用该索引。
- **开启SQL安全更新模式**：通过设置`**sql_safe_updates**`为1，可以防止执行没有显式使用键或`**LIMIT**`子句的`**UPDATE**`和`**DELETE**`语句。这有助于避免意外改动大量数据。
- **使用LIMIT子句**：在不确定具体影响行数时，可以在`**UPDATE**`语句中使用`**LIMIT**`子句来限制影响的行数。
- **监控和测试**：在对生产数据库执行`**UPDATE**`操作前，先在测试环境中执行，并监控执行计划和锁的行为，确保语句按预期执行。

## 记录锁+间隙锁可以防止删除操作导致的幻读吗？

### 幻读

- 幻读是指在同一事务中，连续执行相同的查询语句时，由于其他事务的插入或删除操作，返回不同的结果集。例如，如果一次查询返回了5行数据，而下一次相同的查询返回了6行，就发生了幻读。

### InnoDB如何处理幻读

1. **针对快照读**（例如普通的`**SELECT**`语句）：InnoDB通过MVCC（多版本并发控制）来解决幻读问题。在可重复读隔离级别下，事务看到的是在事务开始时的数据快照，即使期间有其他事务进行了插入或删除操作，这些改动也不会影响到当前事务的查询结果。
2. **针对当前读**（例如`**SELECT ... FOR UPDATE**`）：InnoDB通过使用next-key锁来处理。这种锁同时锁定记录本身和记录之间的间隙，防止其他事务在锁定的范围内插入新记录。

## 乐观锁vs悲观锁

- 核心思想：假设系统中的并发冲突是少发生的，数据在操作时不加锁，只在数据提交时进行冲突检查和数据更新。
- 特点：
    - 避免了长时间的数据锁定，降低了死锁的可能性。
    - 提高了系统的并发处理能力。
    - 可能存在多次重试的开销，特别是在高并发的场景下。
- 实现方式：
    - 版本号（Versioning）：在数据表中增加一个版本号字段。读数据时，取出版本号。数据更新时，带上版本号，更新数据前检查版本号是否发生变化，如果没有变化则更新数据并增加版本号；否则重试。
    - 时间戳：使用时间戳代替版本号，工作原理类似。
- 适用场景：适用于读多写少，冲突少的场景。

- 核心思想：假设系统中的并发冲突是频繁发生的，因此在数据操作之前先加锁，确保同一时刻只有一个事务能操作数据。
- 特点：
    - 数据的一致性和安全性较高，因为在数据操作期间，其他事务不能操作该数据。
    - 可能导致事务长时间等待，降低了系统并发处理的能力。
    - 增加了死锁的风险。
- 实现方式：
    - 数据库自带的锁机制：如行锁、表锁等。
    - SELECT FOR UPDATE：在查询语句中使用此子句可以对查询到的数据加锁，直到事务结束才释放锁。
- 适用场景：适用于写多或者读写混合型的业务，以及需要高度数据一致性的场景。

  

## MVCC 与隔离级别

MVCC 的实现原理（Read View、版本链、可见性判断）以及各隔离级别下脏读、不可重复读、幻读的表现与解决方法，详见 [[事物|事务]] 卡片。

锁与 MVCC 的协作关系：
- **快照读**（普通 SELECT）：通过 MVCC 读取历史版本，不加锁
- **当前读**（SELECT FOR UPDATE、UPDATE、DELETE）：读取最新版本，加行锁
- RR 级别下，MVCC 解决快照读的幻读，Next-Key Lock 解决当前读的幻读
